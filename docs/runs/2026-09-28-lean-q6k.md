# lean engine, Q6_K tensor support (Qwen2.5-3B-Instruct)

Adds Q6_K to `gguf.rs`/`quant.rs`/`cpu_kernels.rs`/`model.rs`/`cpu.rs`: GGUF
block parsing, a GPU matmul/matvec kernel (`shaders/linear_q6k.wgsl`), a GPU
embedding-gather kernel (`shaders/embed_gather_q6k.wgsl`), row-chunking under
the device's storage-buffer-binding limit (`quant.rs::chunk_rows_q6k`), and a
CPU-rung dot kernel (`cpu_kernels.rs::dot_q6_k`, NEON/simd128/scalar
dispatch). Closes the gap flagged in the previous Qwen3/llama sessions:
the official Qwen/Qwen2.5-3B-Instruct-GGUF "q4_0" file failed to load with
"unsupported GGML dtype code: 14" because its `output.weight` tensor is
Q6_K.

## Parameters

- Model: Qwen2.5-3B-Instruct, official `qwen2.5-3b-instruct-q4_0.gguf`
  (36 layers, hidden 2048, heads 16, kv_heads 2, head_dim 128, intermediate
  11008, vocab 151936). Verified tensor dtypes via gguf-py:
  `token_embd.weight` Q4_0, `output.weight` Q6_K (1 tensor), 253 other
  weight tensors Q4_0, 181 F32 (norms/biases).
- Fixture: `crates/lean/reference/fixture_qwen25_3b.json`, 3 cases (short/
  long/non_english, same prompts as `fixture.json`), generated by
  `reference/gen_fixture_qwen25_3b.py` against HF transformers'
  `AutoModelForCausalLM.from_pretrained(..., gguf_file=...)` (CPU, float32,
  greedy decode, top-20 prefill logits) on the GPU box.
- Q6_K dequant unit fixture: `crates/lean/reference/q6k_reference_blocks.json`,
  8 real Q6_K super-blocks extracted from `output.weight` (start/middle/end
  offsets), dequantized with gguf-py's own reference
  (`gguf.quants.dequantize(..., GGMLQuantizationType.Q6_K)`) via
  `reference/gen_q6k_fixture.py`.
- Native: GPU box, RTX 3080, Vulkan backend via wgpu 26, rustc 1.95.0,
  `lean-cli` fast-kernel path. One GPU job at a time (`box.lock`); GPU
  compute-app list empty (idle) during the timing run below.
- CPU rung: NEON/simd128 kernels compiled in but not exercised on this run
  (the GPU box is x86_64; NEON needs aarch64, simd128 needs wasm32+simd128).
  Verified by construction (reuses the existing `dot16_signed_i8` widen
  helper the Q4_0/Q8_0 NEON/simd128 paths already use, checked against the
  scalar path by `cpu_kernels::tests::q6k_dispatch_matches_scalar_reference`
  on whichever path actually compiles) and by code review against
  `gguf.rs::dequantize_q6_k`, not by a same-architecture SIMD-vs-scalar
  test run.
- Browser: not run this session (the Mac is busy) - the wasm lib target
  builds (`cargo check --target wasm32-unknown-unknown -p lean --lib
  --no-default-features --features web`, clean) but no `wasm-pack build` /
  browser harness run happened. `crates/lean/www/` already has an
  `index.html` page pattern from the Qwen2.5/Qwen3 sessions; a
  Qwen2.5-3B-specific page (env-driven GGUF/tokenizer URLs, matching
  `www/main_qwen3.js`'s shape) is not yet created - left for the next
  session that has browser time.

## Observations

- Qwen2.5-3B-Instruct's official "q4_0" GGUF loads and runs token-exact
  end to end once `output.weight`'s Q6_K residency is supported - the
  gap this session closes. `token_embd.weight` stays Q4_0 in this file (so
  `embed_gather_q6k.wgsl` isn't exercised by this fixture), but the crate's
  Q6_K embedding-gather path exists for models where the embedding itself
  is Q6_K (SmolLM2-1.7B-Instruct's own "Q4_0" GGUF, per `gguf.rs`'s
  `GgmlDtype` doc comment - not fixture-tested this session, see Parameters).
- `linear_q6k.wgsl` is a single naive per-output-element kernel (no tiled/
  decode-specialized variant, unlike Q4_0's three-kernel split): Q6_K is
  only ever the lm head in this crate's models, one matmul per forward, so
  prefill and decode dispatch counts are identical (543-544) and decode
  cost (84-85 ms/tok) is roughly flat across the three cases despite
  prefill ms/tok dropping with longer prompts (23.46 to 9.14-10.92, the
  fixed per-forward dispatch overhead amortizing over more prefill rows).
- The Q6_K dequant math (`gguf.rs::dequantize_q6_k`) matches gguf-py's own
  reference bit-for-bit within float rounding on real model blocks (max
  diff < 1e-3 on all 8 sampled blocks, spanning the start/middle/end of
  `output.weight`), not just on synthetic test bytes - the unit-test gate
  this kind of block-layout work needs before trusting the GPU/CPU kernels
  built on top of it.
- CPU-rung Q6_K (`cpu_kernels::dot_q6_k`) reuses the existing NEON/simd128
  16-lane signed-i8 widen helper for the actual multiply-accumulate,
  scalar-unpacking each half-block's four value groups first (the 6-bit
  bit-assembly doesn't vectorize onto a single fixed shift/mask the way
  Q4_0/Q8_0's nibble/byte unpacks do) - not verified by a same-architecture
  SIMD run this session (the GPU box is x86_64), only by the scalar-vs-
  dispatch unit test on whichever path compiles and by code review against
  the reference dequant.
