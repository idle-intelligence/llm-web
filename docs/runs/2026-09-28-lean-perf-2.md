## Change this session

Split-K ("flash-decoding") decode attention: `crates/lean/src/shaders/
attn_decode_split.wgsl` (pass 1, per-`(head, split)` partial online-softmax
over a chunk of keys) and `attn_decode_reduce.wgsl` (pass 2, online-softmax
merge of the partials), dispatched by `model.rs::attn_decode` instead of
the single-workgroup `attn_decode.wgsl` once `kv_len > SPLIT_CHUNK` (128).
Split count `num_splits = min(MAX_SPLITS=32, ceil(kv_len / 128))`, chosen
from `kv_len` alone, never a timing measurement. `workgroup_size(HEAD_DIM)`
stays in {64, 128} on both kernels, inside WebGPU's guaranteed 64-256 range
on every implementation; no subgroup/wave ops. Below `SPLIT_CHUNK`, the
unchanged single-workgroup kernel runs (no split/reduce overhead added at
short context).

## Observations

- The split-K change removes essentially all of the decode-time growth
  with context length that `2026-09-28-lean-long-context.md` documented
  for the single-workgroup kernel: Qwen2.5's `long_tools_single`/
  `long_tools_multiturn` decode drops from 70.30/65.83 ms/tok to
  34.68/34.47 ms/tok - now statistically indistinguishable from the
  short-prompt cases (33-36 ms/tok) on this box. Short-context cases
  (kv_len <= 128) are unaffected as designed (they never dispatch the
  split path).
- Qwen3-1.7B's improvement at `long_tools_single` is smaller in relative
  terms (-10.5% vs Qwen2.5's -50.7%). Qwen3-1.7B's `head_dim`=128 and
  `n_kv_heads`=8 (vs Qwen2.5's 64/2) mean attention is a smaller share of
  total decode cost relative to the QKV/FFN matvecs at 2048 hidden width,
  28 layers - the split-K change only touches the attention dispatch, so
  a model where attention is proportionally cheaper sees a
  proportionally smaller win. This is consistent with, not contradicting,
  the flash-decoding mechanism: it removes the attention-specific
  O(kv_len) serial cost, and that cost is a smaller fraction of this
  model's per-step total.
- The `long_tools_single` fixture case for Qwen2.5 fails `lean-cli`'s
  standalone greedy-continuation token match (`tok=false`) on *both*
  before and after builds, with an identical divergent token sequence in
  both runs - confirmed by running the unmodified `lean-engine` tip
  through the same `lean-cli` invocation as a control. This is a
  pre-existing `lean-cli`/fixture-loop artifact (the model does not stop
  generating at the same point `lean-cli`'s standalone driver expects),
  not a split-K regression, and not the same thing as `cargo test
  --ignored`'s `fixture_parity_*` tests, which check top1/top20 logit
  agreement and passed cleanly on this exact model/fixture pair. `top20_maxdiff`
  for this case (0.000063) is unchanged between before and after.
- `llama.cpp`'s Vulkan decode throughput (609.48 tok/s Qwen2.5-0.5B,
  269.41 tok/s Qwen3-1.7B, both `pp2225`-adjacent context) is far above
  this session's post-split-K lean numbers (28.8 tok/s / 1000/34.68,
  8.1 tok/s / 1000/123.38): roughly 21x and 25x respectively. Split-K
  closed the length-dependent gap (decode no longer grows with context)
  but did not touch the length-independent per-step cost, which step 3
  (Q4_0/Q8_0 matvec efficiency) targets next - `llama.cpp`'s
  per-token cost is dominated by an optimized quantized-matvec kernel,
  the same kernel class flagged as the next step in
  `2026-09-28-lean-perf.md`'s own observations.
- `llama.cpp` had to be built from source for this comparison: the box had
  no system Vulkan SDK package (`find_package(SPIRV-Headers)` failed), so
  `SPIRV-Headers` was built from source into a local, non-system prefix
  into a user-level prefix (no `sudo` used, per this
  task's box constraints) and its headers made visible to the compiler
  via `CPLUS_INCLUDE_PATH`/`C_INCLUDE_PATH` (the upstream
  `ggml-vulkan/CMakeLists.txt` calls `find_package(SPIRV-Headers CONFIG
  REQUIRED)` but never links the resulting imported target into
  `ggml-vulkan`, so its own `find_package` success does not by itself put
  the headers on the include path).

### Re-profile: what dominates decode now (Qwen3-1.7B, `long_tools_single`, 2225 prompt tokens)

Method: disable/double one kernel class at a time in a scratch build,
never a timing-driven kernel choice - the dispatch selection itself is
still capability-gated as before, this is diagnostic only. 2 repeats per
configuration.

- **lm head kernel**: `decode_layers`'s `dec_lm_head` call hardcodes
  `fast=false`, so the lm head (`output.weight`, the single largest
  matvec at `vocab_size=151936` rows) always uses the generic
  `linear_q8.wgsl` kernel even after this session's change, on every
  model. Flipping that to `model.fast_kernels` (so it uses
  `linear_q8_decode.wgsl` too) and re-running Qwen3-1.7B: decode dropped
  from 58.97-59.26 (baseline, 2 runs) to 54.89 ms/token, `tok_match`/
  `top1`/`top20_maxdiff` unchanged. That is a further ~7-8% of decode
  time from one hardcoded flag, not yet fixed in the committed code this
  session (flagged as next target, not applied - see below).
- **Attention (doubled `attn_decode` dispatch per layer)**: baseline
  (2 runs) 59.26/59.05 ms/token; doubled (2 runs) 61.86/62.37 ms/token.
  Delta ~2.96-3.07 ms, i.e. attention is roughly 5% of decode time at
  2225 prompt tokens post-kernel-change. At short context (15 prompt
  tokens): baseline (2 runs) 54.15/48.31 (noisy, ~6 ms spread); doubled
  (2 runs) 55.35/55.31 (tight). Delta ~4.1 ms off a ~51-55 ms baseline,
  roughly 7-8%. Both estimates are within a few ms of the doubling
  method's own noise floor (the short-context baseline pair alone spans
  ~6 ms) - reported as rough shares, not precise percentages.
- With the lm head and attention contributions each accounted for (~7-8%
  and ~5-8% of decode respectively), the remaining ~85-88% of decode time
  is the per-layer QKV/O/MLP `linear_q8_decode.wgsl` dispatches (5 linear
  calls x 28 layers) plus RMSNorm/RoPE/add/silu elementwise kernels and
  their dispatch overhead - not broken down further into individual
  kernel classes this session.

### Step B: wider (vec4&lt;u32&gt;) weight loads in decode matvec kernels (attempted, reverted)

Measure-first pass (per the brief's order): the existing per-layer
decode dispatch breakdown from Session 3's re-profile (lm head ~7-8%,
attention ~5-8%, remaining ~85-88% split across the per-layer
`linear_q4_decode.wgsl`/`linear_q8_decode.wgsl`/norm/rope/add dispatches)
was reused rather than re-run, since it already isolates the target: the
per-layer matvec kernels are the dominant cost and were the next
concrete, scoped target per that session's own conclusion.

Rewrote `linear_q4_decode.wgsl` and `linear_q8_decode.wgsl` to bind `qs`
as `array<vec4<u32>>` and assign each of the 32 lanes/row a strided set
of whole *blocks* (loading one vec4 = a Q4_0 block's full 16 bytes, or
half a Q8_0 block's 32 bytes, per load) instead of the original
strided-by-individual-word assignment (4 separate scalar `u32` loads per
lane per outer-loop pass). Dequant math unchanged; both changes reorder
summation (block-major instead of word-major accumulation across the 32
lanes), which is within this crate's existing fixture-parity tolerance
(confirmed by the gate below, not just assumed). Gated clean (both
clippy targets, full 12-test ignored suite token-exact).

Measured decode ms/token, before (04ae46b, original word-striped kernels)
vs after (vec4 block-striped kernels), Qwen2.5-0.5B (Q4_0-resident, so
this exercises `linear_q4_decode.wgsl` on every per-layer call):

| case | prompt tokens | before | after | delta |
|---|---:|---:|---:|---:|
| short | 36 | 24.12 | 27.10 | +12.4% |
| long | 86 | 23.71 | 26.67 | +12.5% |
| non_english | 54 | 23.29 | 26.16 | +12.3% |
| long_tools_single | 2225 | 24.33-24.38 | 27.63 | +13.4% |
| long_tools_multiturn | 2354 | 24.23 | 27.56 | +13.7% |

A consistent ~12-14% **regression**, not an improvement, across every
case. **Not adopted**: reverted both shader files via `git checkout` back
to the pre-experiment (`04ae46b`) state. No commit made for this step.
Total per-lane data movement is identical between the two versions (same
words, same total bytes); the likely cause (not instrumented further
this session) is the dynamic-index array extraction pattern
(`array<u32,4>(words4.x, words4.y, words4.z, words4.w)` then indexing it
with a loop variable) that the vec4 rewrite requires to unpack a loaded
vector back into scalar words - this same pattern already exists in
`linear_q4_tiled.wgsl`'s dequant loop, which Session 1 of this doc
independently measured at only ~4.7% of GPU peak despite its vec4
loads, consistent with dynamic vector-component indexing being the
actual cost, not load width.

Two data points this session (this one and Step A) both suggest that,
on this GPU, the existing decode/prefill matvec kernels' bottleneck is
not raw load width or tile size in the way both t0-web's and llm-web's
own kernel designs assumed - something more specific to this crate's
kernel shapes or this GPU's memory controller. Neither the QKV-fusion nor
gate/up-fusion part of step B, nor step C (Q8_0 KV cache), were attempted
this session: the brief's own ordering makes C conditional on A and B
landing, and B's only concrete sub-experiment attempted here regressed
rather than improved.

### Step 4: llama.cpp Vulkan `mul_mat_vec` shader survey (no commit)

Read `ggml/src/ggml-vulkan/vulkan-shaders/mul_mat_vec_base.glsl`,
`mul_mat_vec.comp`, `mul_mat_vecq.comp` and `mul_mat_vecq_funcs.glsl` in the
box's llama.cpp checkout (build `ed7ac35`, MIT-licensed, "Copyright (c)
2023-2026 The ggml authors" - read-only reference, no code copied
verbatim into this crate). Techniques identified, in order of estimated
contribution to the ~15-25x native decode gap documented in sessions 2-4:

1. **Integer dot product on quantized activations** (`mul_mat_vecq.comp`,
   used for Q4_0/Q8_0's "legacy" quant path): the activation vector is
   dynamically quantized to Q8_1 blocks (int8 + scale) on the fly, then
   the dot product against the int8/int4-packed weight runs as an integer
   dot instruction (`GL_EXT_integer_dot_product`) instead of a
   dequant-to-f32-then-multiply-add. This is the single largest
   architectural difference from this crate's decode kernels (which
   dequantize weights to f32 registers and multiply against f32
   activations) and the most plausible explanation for most of the
   remaining gap - GPUs with native int8 dot-product ALUs get several
   values per instruction instead of one f32 FMA per value.
2. **Rows per workgroup** (`NUM_ROWS`, a `constant_id` specialization
   constant): one workgroup computes several output rows at once,
   amortizing the workgroup's other fixed costs (barrier, launch) across
   more output. This crate's `linear_q4_decode.wgsl`/`linear_q8_decode.wgsl`
   already does this (`ROWS_PER_WG = 4`) - not a gap, already adopted
   (ported from llm-wasm before this session).
3. **K-splitting across threads with a manually-unrolled inner loop**
   (`K_PER_ITER` = 8 for Q4_0/Q8_0's legacy format, threads split the
   row's K dimension and each accumulates a strided partial sum, unrolled
   4x/2x/1x per outer iteration). This crate's decode kernels already
   split K across 32 lanes/row with a 4x-unrolled inner loop - same
   mechanism, already adopted.
4. **Subgroup reduction** (`subgroupAdd`, `GL_KHR_shader_subgroup_*`) for
   the final cross-thread reduce, with a shared-memory tree-reduction
   fallback when subgroups aren't used. This crate's own portability rule
   (no subgroup/wave ops, so the same kernel runs unmodified on every
   WebGPU implementation) rules this one out; this crate's decode kernels
   already use the portable shared-memory tree-reduction fallback llama.cpp
   itself falls back to - same mechanism, already adopted, minus the
   subgroup fast path this crate deliberately forgoes for portability.
5. **One dispatch per linear layer, not per tensor** - orthogonal to this
   survey (llama.cpp's own dispatch count wasn't inspected; this is what
   step 3's gate/up fusion targets in this crate).

**Adopted this session**: none. Techniques 2-4 were already present before
this session (ported from llm-wasm in earlier sessions, not from this
survey). Technique 1 (integer dot on quantized activations) is the
concrete, portable-in-principle candidate for a future session - WebGPU's
current spec has `dot4I8Packed`/`dot4U8Packed` builtins that could serve
the same role as `GL_EXT_integer_dot_product`, but adopting it needs (a) an
online activation-quantization kernel (Q8_1-style, not currently
implemented anywhere in this crate) inserted before every decode matvec,
(b) verifying `wgpu`/`naga`'s current pinned version actually lowers
`dot4I8Packed` correctly on every backend (Metal/Vulkan/DX12), and (c) a
fixture-parity re-validation at whatever quantization tolerance the online
Q8_1 pass introduces - out of scope for this session's remaining budget,
flagged as the next concrete target.
