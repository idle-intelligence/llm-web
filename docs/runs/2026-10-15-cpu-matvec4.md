# CPU Q4_0/Q8_0 matvec: four rows per pass (NEON, wasm simd128)

Change: the one-row CPU matvec for Q4_0 and Q8_0 weights (`cpu_kernels.rs`, `dot_rows` and `matvec_q`) loads each 32-value activation block once for four weight rows, accumulates each row's block sums times the block scale in four lanes, and does one horizontal sum per row (before: one horizontal sum per 16 weights and a scalar accumulation per block). Activations stay f32. The one-row `linear` and the 32-column team items of the threads backend call it; one to three leftover rows take the one-row instance of the same code. The multi-row (prefill) path, the scalar build and the other weight types are unchanged.

## Parameters

- Before: `browser-perf` at cc92176. After: the same plus the kernel commit, rebased onto `browser-perf` 1199050 (a run-doc commit only, no code change between the measured source and the rebased one).
- Machine: the M2 laptop (16 GB), shared with other workers; every timed run waited for a 1-minute load below 3 and no rustc/cargo process, and held the build lock (native) or the browser lock (browsers). Rust 1.99.0 (pinned toolchain), release builds, no `RUSTFLAGS`.
- Kernel harness: `bench/cpu-matmul` from the `cpu-matmul` branch (lean against the Candle fork, see the 2026-10-15 cpu-matmul run doc), outside the repository, with `cpu_kernels.rs` of the before tree as `old` (one-row `linear`, per-row dots) and of the after tree as `new` (`matvec_q` over all rows), the fork as before. Matvec (M=1) only, synthetic Q4_0/Q8_0 blocks, `hot` and `stream` modes, median of 7 samples per case, best of two runs (A, B). Native 1 thread and wasm32 simd128 in Node v20.9.0. Load at the start of native A, wasm A, native B, wasm B: 2.64, 2.11, 2.13, 2.21. The harness also counts, for every output, whether `new` differs in any bit from the new one-row dot of that row.
- Native decode: a scratch example (not committed) on lean-core's `CpuModel`, `threads` feature off (one thread), 36-token synthetic prompt, 48 greedy steps, context 256; each invocation runs one warm-up and 3 timed repetitions and reports their median ms per token. Five invocations per build, before and after interleaved (ABAB), table gives the median, min and max of the five. Load at the invocations 1.88 to 2.93.
- Browsers: `scripts/bench` (bench.html, bench_worker.js) served by `serve.mjs` with cross-origin isolation, with one local change to the worker that is not committed: `backend=threads` loads `pkg-mt` and calls `initThreadPool(navigator.hardwareConcurrency)` (8), any other non-WebGPU value loads `pkg` (single thread). Phases `decode,exact,sampled`, 128 greedy tokens, sampled 128 tokens with the chat page's sampler (temperature 0.7, top-k 40, top-p 0.9, repetition penalty 1.1, seed 0). Playwright Chromium 153 (headless), Playwright WebKit (Safari 26.6 build, headless), Firefox Developer Edition 159 (headed, throwaway profile, puppeteer-core). One load per cell for the three-browser table (load 2.06 to 2.99); Chromium also ABAB, five loads per build and cell, phases `decode` (greedy 128 tokens) and the exactness phase (load 1.80 to 2.94).
- Builds: `scripts/build.sh` with `BUILD_THREADS=1`, ENGINE_BUILD `2026-10-15-matvec4-base` (before) and `2026-10-15-matvec4-01` (after, also the tag committed on every loading URL). Served wasm, fetched back from each server, md5: before `pkg` 73e81bfa39c2282539e55557a77d8870, `pkg-mt` 9e8775bebd9ac6a9e9f8616fc9792d9e; after `pkg` 649569c777ec820eb906947495b2e27d, `pkg-mt` a483a626c63beb99fc6ee0fcd93b25a0, equal to the built files. Both pass `check_wasm_features.py` (+simd128, and +atomics for pkg-mt).
- Device page: `web/device/index.html` from the after `_site`, "CPU threads" then "Single CPU thread" clicked, model downloaded by the page (SmolLM2-360M-Instruct Q4_0), in the same three browsers.
- Models: Qwen2.5-0.5B-Instruct Q4_0, SmolLM2-360M-Instruct Q4_0 and Q8_0, Qwen3-0.6B Q4_0 (native); Qwen2.5-0.5B-Instruct Q4_0 and SmolLM2-360M-Instruct Q4_0 (browsers).
- Reference hashes: the GPU (WebGPU) hashes of the 2026-10-15 merged build in `2026-10-12-lean-browser-perf.md`, whose exactness and greedy runs match transformers through the fixture gates.

## Observations

- Native, one thread: decode is 1.18x to 1.21x faster on the four files (Qwen2.5-0.5B Q4_0 13.7 to 16.6 tok/s, SmolLM2-360M Q4_0 15.8 to 18.8, Q8_0 19.6 to 23.1, Qwen3-0.6B Q4_0 10.7 to 12.9), with the min-max ranges of before and after not overlapping in any of the four. The kernel harness gives 1.11x to 1.23x for the matvec alone, so the decode gain is about what the matvecs give. Per shape, natively, new against old ranges from 0.94x to 1.28x; 4 of the 60 native cases are below 1.0x (the native runs are the noisier platform, see the spread in the cpu-matmul run doc); in wasm every case is faster (1.16x to 1.42x). The end-to-end decode is the measure that counts here; prefill (the multi-row path, unchanged) moves by less than 4%.
- wasm32 simd128 in Node: the matvec is 1.25x to 1.32x faster (geometric mean), which closes most of the distance to the Candle fork on Q4_0 (fork 1.34x to 1.37x over the old kernel) and part of it on Q8_0 (fork 1.49x to 1.58x). Natively the fork remains about 2x faster than the old kernel, against 1.11x to 1.23x for the new one; the rest of that gap is the fork's 8-bit activations.
- Browsers, Chromium ABAB: single thread 12.7 to 14.7 tok/s (Qwen2.5-0.5B, 1.16x) and 11.1 to 12.7 (SmolLM2-360M, 1.14x), with non-overlapping ranges. The threads backend shows 1.14x and 1.13x on the medians, but one load of each build fell to about half speed (19.6 and 22.5 tok/s for Qwen2.5-0.5B, 22.9 and 25.7 for SmolLM2-360M), so its ranges overlap and the threads numbers are less certain than the single-thread ones.
- Browsers, one load per cell: the after build is faster in 22 of the 24 cells (single thread 1.10x to 1.25x in all three browsers); the two exceptions are WebKit SmolLM2-360M threads greedy (24.8 against 24.5) and Firefox Qwen2.5-0.5B threads sampled (10.8 against 10.5). The one-load browser table was taken while the machine was busier than during the Chromium ABAB series: the same Chromium cells read 8.5 and 19.2 tok/s there against 12.7 and 37.2 in the ABAB medians.
- Firefox Developer Edition's threads backend in the bench harness ran at 10 to 13 tok/s, close to its single-thread rate, before and after alike, while the device page in the same browser gave 43.5 tok/s on threads. Not investigated here; it does not depend on this change.
- Output: every browser cell (3 browsers, 2 backends, 2 models, before and after) gives the exactness, greedy 128 and sampled 128 hashes of the GPU backend of the merged build; native greedy token hashes are equal before and after; the device page reports token-exact against transformers on both CPU backends in the three browsers. The four-row pass equals the one-row dot bit for bit in every harness case (native and wasm) and in the unit tests, and the threaded decode-shaped `linear` equals single thread for a width with a three-row tail.
- cpu_lora_parity fails on the after build at its last step (CPU against GPU base model after clear_lora, 1.593e-2 against a 1e-2 limit) and fails identically on the before build. The CPU side agrees with HF+PEFT to 3.2e-4; the difference is on the GPU side (5.8e-2 against HF+PEFT), outside this change.
- Not run: the real Safari app (only Playwright WebKit ran), the Linux test machine and x86, Android browsers, the Llama-3.2 CPU fixtures.
