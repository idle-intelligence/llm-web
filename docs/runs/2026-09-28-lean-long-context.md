# lean engine: long-context attention correctness

Follow-on to `docs/runs/2026-09-28-lean-kv-mask.md` and
`docs/runs/2026-09-28-lean-perf.md`. Same crate (`crates/lean`), same
model/fixture, macOS 26.3.1, Apple M2. The Sonos MCP agent's real prompts
run 1,000-2,000+ tokens; `attn_prefill.wgsl`'s fixed `MAX_SEQ = 256` and
`attn_decode.wgsl`'s fixed `scratch: array<f32, 2048>` meant every prompt
past those lengths got wrong (silently incomplete) attention output. This
session replaces both with length-independent kernels and adds reference
fixtures built from the agent's actual inputs to prove it.

## Parameters

- Model: Qwen2.5-0.5B-Instruct, `qwen2.5-0.5b-instruct-q4_0.gguf` (Q4_0
  weights, Q8_0 `output.weight`), tokenizer `Qwen/Qwen2.5-0.5B-Instruct`.
- Config: 24 layers, hidden 896, 14 heads, 2 KV heads, head_dim 64,
  intermediate 4864, vocab 151936, rope_theta 1e6, rms_norm_eps 1e-6.
- Fixture: `crates/lean/reference/fixture.json`, generated by

  `transformers.AutoModelForCausalLM.from_pretrained(..., gguf_file=...)`,
  same Q4_0 GGUF dequantized on load, 32-token greedy continuation each).
  Five cases: `short` (36 tokens), `long` (86), `non_english` (54) -
  pre-existing - plus two new long-context cases this session:
  - `long_tools_single` (2225 tokens): the Sonos MCP agent's real
    `(messages, tools)` input from
    `fixtures/reference/inputs/02_tools_single.json` at the repo root
    (system + user "pause the kitchen", 12 real Sonos MCP tool schemas),
    already chat-templated and tokenized (with `tools=...`) into
    `fixtures/reference/rendered/02_tools_single.tokens.json`.

- Kernel path: `fast_kernels = true` on both native and browser, plus the
  `false` (naive Q4_0 kernel, unaffected by this session's linear kernel
  work) path on native for parity coverage.
- Native: macOS 26.3.1, Metal backend via wgpu 26, `LEAN_GGUF`/
  `LEAN_TOKENIZER_DIR` pointed at
  the local models directory (GGUF and tokenizer).
- Browser: Playwright-bundled Chromium (headless), `--enable-unsafe-webgpu
  --enable-features=Vulkan,WebGPU --use-angle=metal`, model served locally
  (`?local=1`) from `python3 -m http.server` rooted at `crates/lean/`.
  Engine build tag `2026-09-28-6`. `lean_bg.wasm` sha256
  `c5ea389097c18b0486822181c2d16f6b4f268f9bb44a33cd4a7d226c5cd3da20`

- One GPU job at a time throughout; native and browser runs never
  overlapped.

## The fix

- `attn_prefill.wgsl`: replaced the per-workgroup `scores: array<f32,
  MAX_SEQ>` (one workgroup per head, `workgroup_size(256)`, one thread per
  query row - rows >= 256 never got dispatched at all) with a
  flash-attention-style online (running) softmax: each thread keeps only a
  scalar running max/sum plus a `head_dim`-sized accumulator in registers,
  no per-row score storage. Dispatch changed from `(n_heads, 1)` to
  `(n_heads, ceil(seq/256))` - one workgroup per 256-row query tile - so
  GPU thread count scales with `seq` instead of staying fixed. An
  intermediate version kept the old `(n_heads, 1)` dispatch with each
  thread grid-striding over multiple rows; that serialized too much
  per-thread work at 2225+ tokens and triggered a native Metal `device
  poll failed: Timeout`, fixed by the 2D dispatch instead.
- `attn_decode.wgsl`: replaced the `scratch: array<f32, 2048>` (one slot
  per key, capping `kv_len` at 2048) with a tiled online softmax over
  `WG`-sized (64) key tiles, reusing the same small shared array every
  tile - shared-memory use no longer depends on `kv_len` at all.
- Both kernels' `-f32::MAX` sentinel literal (`-3.4028235e38`) parses on
  native's naga validator but not on Chrome's Tint WGSL validator (`value
  ... cannot be represented as 'f32'` - the literal rounds a hair past the
  true `f32::MAX`), which failed WebGPU compute pipeline creation outright
  in the browser. Replaced with `-1e30` (effectively -infinity for any
  real attention score, parses on both).
- `kv_snapshot_restore_matches_full_prefill_and_round_trips` (native test)
  was hardcoded to the fixture's 86-token case (split 43/43) - nowhere
  near the old caps. Now picks the fixture's longest case (2354 tokens,
  split 1177/1177).

## Observations

- The two long-context fixture cases are token-exact against the HF
  transformers reference on both native kernel paths and in the browser -
  the original bug (silently wrong output past 256 tokens) is fixed, not
  just made to run without crashing.
- Browser prefill throughput at real long-context lengths (2225/2354
  tokens: 124.1/103.6 tok/s from this run; see
  `docs/runs/2026-09-28-lean-perf.md`'s appended table for the
  vec4-GEMM-kernel comparison) is far under the 1,000 tok/s target. This
  is now a *correct* O(seq^2) causal-attention cost that the old buggy
  kernel never actually paid (it silently dropped all but the first 256
  query rows' worth of attention work) - it should not be compared
  directly against this session's or the prior perf doc's shorter-prompt
  numbers as if it were a regression; it is the true cost of correct
  attention at this length with today's per-thread (no K/V tiling across
  threads) kernel design. Closing this gap needs a genuinely tiled
  flash-attention kernel (shared-memory K/V reuse across query threads in
  a workgroup), which this session did not attempt.
- Decode ms/token grows with `kv_len` as expected for `attn_decode.wgsl`'s
  per-tile loop (`WG=64` keys per tile): 26.5-26.8 ms/tok under 100 tokens
  of context, up to 75.8-264.0 ms/tok at 2225-2354 tokens of context. The
  two long cases' decode numbers vary more between browser runs (99.5 vs
  264.0 ms/tok for `long_tools_single` across two runs) than the
  short-case numbers do - likely GC/memory-pressure noise from the
  preceding multi-gigabyte-scale long prefill in the same page, not
  isolated here.
- `kv_snapshot_timing_1000_token_prefix`'s full-prefill number (19645.80
  ms native, ~1235 tokens) is now a genuine full-length-correct timing,
  where before this session it was timed against a known-incomplete
  attention output (same caveat the perf doc's own `long_1000` case
  carried). The round-trip speedup (193.2x) is a snapshot/restore-vs-
  full-recompute comparison and is unaffected either way, since both
  sides of that comparison were already using the same (buggy or fixed)
  attention kernel.
