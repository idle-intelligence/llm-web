# Model vs. port parity check — 2026-09-10

Question: the eval scores ~25% (`eval/results/2026-09-10-summary.md`), mostly
by inventing ids instead of calling the listing tool first. Is that the
**model** (xLAM-2-3b-fc-r) or the **port** (Burn+wgpu, Q4_0 GGUF)?

Method: for 8 cases, render `[system, user(utterance)]` + the 12-tool set
with the DEFAULT system prompt via `apply_chat_template(add_generation_prompt=True)`,
tokenize identically for both sides, and run **greedy** decoding on the
byte-identical token ids on each side, independently of the eval harness's
multi-step/tool-execution/prefix-cache machinery — this isolates "does the
model/port pick the same first token(s)" from any bug in how the eval
harness drives either one.

## Parameters

- HF side: `Salesforce/xLAM-2-3b-fc-r`, unquantised weights, bfloat16, MPS, `do_sample=False`, `use_cache=True`, `max_new_tokens=64`.
- Port side: `./target/release/llm-agent run --gguf .../xLAM-2-3b-fc-r-q4_0.gguf --tokens <id>.tokens.json --max-new 64 --tokenizer .../tokenizer.json`, Burn+wgpu native backend, Q4_0-quantised weights dequantised to f32 at load, greedy (the port has no sampling path).
- Repo commit: 5fb62be.
- System prompt (both sides): "You are a helpful home assistant with access to Sonos speaker controls."
- Tools: `fixtures/sonos/tools-12.json` (12-tool subset), converted MCP->function-calling shape via `make_inputs.mcp_to_function_tools`.
- Prompt tokens per case (identical on both sides — same tokenizer, same render): s01=2228, s02=2227, s06=2228, s08=2226, s09=2225, m01=2226, m04=2229, m07=2230.
- Rendered/token artifacts: `<repo-root>/tmp/parity/<id>.{rendered.txt,tokens.json,hf.json,port.json}`.

## Observations

- 5 of 8 cases (`s02, s06, s08, s09, m01`) are token-for-token identical between HF bf16 and the Q4_0 port through EOS on the identical rendered prompt — for these, the ~25%-correct eval outcome traces to the **model's** choices, not a port defect.
- In the 2 cases where both sides invent a non-canonical id (`s01`, `m07`), the divergence is confined to the id token itself (`"1234"` vs `"1"`; `"bedroom"` vs `"Bedroom"`) — both sides pick the same tool and the same "act without listing" strategy; this is model behavior reproduced by the port, not a port-introduced defect.
- `m04` is the one case with a genuine port-side behavioral divergence: HF's first call is the listing tool (matching the expected pattern), while the port skips straight to `skip_to_next_track` with an invented `"kitchen"` id, diverging at token index 5 (right after the tool-name string closes) — this is the strongest evidence of the port picking a different action than the model would.
- HF shows no observed prompt sensitivity for `m01` across three phrasings (default punctuation, fixture-02-style lowercase, repeat) — all three produce the listing tool as the first call.
