# lean engine, CPU fallback rung (single-threaded)

Plan step list 1-4 from
`~/Code/tracker/projects/llm-web/cpu-fallback-plan-2026-09-28.md`. Crate
`crates/lean`, new modules `src/cpu.rs` (forward pass) and
`src/cpu_kernels.rs` (Q4_0/Q8_0 dot kernels). Same `Qwen2Config`/
`GgufReader`/tokenizer/chat-template code as the GPU path (`model.rs`) -
second rung, not a second model definition.

## Parameters

- Model: Qwen2.5-0.5B-Instruct, GGUF `qwen2.5-0.5b-instruct-q4_0.gguf`
  (Q4_0 weights, Q8_0 `output.weight`), tokenizer from
  `Qwen/Qwen2.5-0.5B-Instruct`.
- Config (from GGUF metadata): 24 layers, hidden 896, 14 heads, 2 KV heads,
  head_dim 64, intermediate 4864, vocab 151936, rope_theta 1e6,
  rms_norm_eps 1e-6.
- Fixture: `crates/lean/reference/fixture.json`, 3 cases used here (`short`
  36 prompt tokens, `long` 86, `non_english` 54), 32-token greedy
  continuation each. The two long-context agent-tool-calling cases
  (`long_tools_single`/`long_tools_multiturn`, 2225/2354 prompt tokens)
  were skipped per the plan's step 1 note ("optional for CPU because of
  time") - not run in this pass.
- Kernel dispatch: compile-time only (`cpu_kernels.rs`) - NEON on aarch64,
  wasm simd128 on wasm32 compiled with `-C target-feature=+simd128`
  (`.cargo/config.toml`, applies to every wasm32-unknown-unknown build in
  this workspace), scalar everywhere else. No runtime feature detection.
- Native: macOS 26.3.1, Apple M2 (aarch64), `cargo build -p lean --release`.
- Browser: Playwright-bundled Chromium ("Google Chrome for Testing"),
  headless, default launch (no WebGPU flags) - `navigator.gpu` was present
  but `LeanEngineCpu` never calls it; this Mac's headless Chromium has no
  real GPU adapter regardless (house rule: never time WebGPU there).
  Model served locally (`?local=1`) from `python3 -m http.server` rooted
  at `crates/lean/`.
- wasm build: `wasm-pack build crates/lean --target web --out-dir pkg
  --features web`. Harness page `crates/lean/www/cpu.html` /
  `main_cpu.js`, engine build tag `2026-09-28-cpu-2`.
  `lean_bg.wasm` sha256
  `d5c9ec13011958a8d9f99ccbc421afb3fc51a73a2f29e4ad5b5bf345ba564c24`
  (3,361,364 bytes). `wasm-tools print lean_bg.wasm | grep -c v128` = 16284.
- One GPU job at a time: the native CPU runs, the browser CPU-only run,
  and the GPU fixture_parity re-check below were not run concurrently.

## Observations

- All three cases are token-exact on both new surfaces: native CPU
  (NEON) against the HF-transformers fixture, and browser CPU (wasm32
  simd128) against the same fixture, with logit drift (`top20_maxdiff`
  0.00003-0.00005) far under the fixture's 1e-3 tolerance - float
  accumulation order differs from both the GPU kernel and the reference,
  as expected, without changing any argmax.
- NEON gives a 5.2x decode speedup over the scalar fallback on this
  machine, measured with the same binary and the same fixture cases
  (`--features force_scalar` swaps only `cpu_kernels`' aarch64 dispatch
  branch, nothing else) - past the plan's step 3 pass bar ("any factor >
  1.0x") and larger than TC's own t0-web wasm-SIMD win (2.26x-2.29x,
  `t0-web/docs/runs/2026-09-22-cpu-simd.md`), though the two aren't the
  same comparison (NEON vs scalar here, wasm simd128 vs wasm scalar
  there, different ISAs and different workloads).
- Native NEON decode (46.6-47.1ms/tok, ~21.3-21.5 tok/s) sits below the
  plan's optimistic bandwidth ceiling (~233 tok/s, 100% of system
  bandwidth) and below its "assumed single-thread fraction" range
  (~47-70 tok/s) - expected, since that range was explicitly flagged as a
  placeholder needing a real measurement, and this reference kernel's
  linear() does `rows * out_dim` independent scalar-driven dot calls with
  no blocking/tiling (the plan's own scope note: a fast CPU kernel is a
  follow-up, this pass is the reference-correctness rung).
- Browser wasm32+simd128 decode (76.6-77.3ms/tok, ~13 tok/s) is
  ~1.6-1.7x slower than native NEON decode on the same machine - the
  expected wasm-vs-native gap (JS/wasm-bindgen call overhead into
  synchronous Rust, plus wasm's own codegen being generally slower than
  native LLVM output for the same source), not investigated further in
  this pass.
- **A real correctness bug was found and fixed during this work**, not by
  the browser run but by cross-compiling `cpu_kernels.rs` alone to
  wasm32-wasip1 (`+simd128`) and running its unit tests under `wasmtime`
  before ever touching `wasm-pack`: the simd128 module's Q8_0 dot kernel
  reused Q4_0's `-8` nibble-offset helper on Q8_0's already-signed bytes,
  corrupting every Q8_0 dot product (the lm head - see `output.weight`'s
  dtype in `model.rs`'s doc comment). NEON never had this bug (it already
  used two separate helpers for the two dtypes). First browser run before
  the fix produced garbled/repetitive greedy output (see the fix commit's
  message) with `tokens_match = false` on all three cases; after the fix,
  all three token-match. This is the concrete instance of this crate's
  stated rule ("parity before perf, every time") catching a real kernel
  bug before it reached a demo page.
- wasm binary: 3,361,364 bytes (`lean_bg.wasm`), 16284 `v128` instructions
  present (`wasm-tools print | grep -c v128`) - confirms simd128 actually
  compiled in and was exercised, not silently falling back to scalar.
- GPU fixture_parity (`fast_kernels` true and false, Qwen2.5-0.5B) still
  passes unchanged after this work - the CPU rung shares config/GGUF
  parsing code with the GPU path but touches none of its wgpu code.
- Not run in this pass (plan's step 1 explicitly makes this optional for
  CPU): the two long-context agent-tool-calling fixture cases
  (2225/2354 prompt tokens) on either CPU surface - at ~46-77ms/token
  this reference kernel's per-token cost times ~2300 prefill tokens plus
  32 decode tokens would be several minutes per case, well past this
  session's iteration budget. `lean-cli --engine cpu --long` and
  `cpu.html?long=1` are wired to run them when that budget exists.

## What the threads rung (plan step 2) needs next

- A real per-core memory-bandwidth measurement on this M2 (STREAM-triad
  or a dot-product-saturation microbenchmark) to replace the plan's
  20-30%-of-system-bandwidth placeholder - this pass's NEON decode number
  (21.3-21.5 tok/s) is the first real single-thread data point to compare
  it against, but linear()'s naive per-row dot-call structure (no
  blocking across output rows, no reuse of a loaded activation vector
  across multiple weight rows) likely leaves real bandwidth headroom
  unclaimed; a tiled/blocked CPU matvec would be the natural next
  optimization before reaching for threads.
- The COOP/COEP-vs-Web-Worker interaction the plan flags (TC's own
  `stt-llm-tts` regression) still needs testing against this crate's own
  Web Worker loading path specifically - not exercised by this pass's
  harness, which runs on the main thread with no cross-origin-isolation
  headers at all.
- A decode-shaped (not GEMM-batch-shaped) wasm-bindgen-rayon prototype to
  get a real number for step 6's threads-vs-single-thread comparison,
  given the plan's stated expectation that decode's poor cross-token
  parallelism may make a thread pool not worth using for decode
  specifically (even if it helps prefill).
