# lean: runtime LoRA, caller-supplied positions/mask, sliced lm-head (2026-09-28)

What llm-life needs from the engine:
runtime LoRA on q/k/v/o over the frozen Q4_0 base, caller-supplied per-token
position ids, a pluggable attention mask, and a sliced lm-head reading logits
at every position: the generic mechanisms llm-life's variant A/B need and
that `crates/lean` did not have before this session (gap #1 KV
snapshot/restore and gap #2 per-step logit mask had already landed).

## Parameters

- Base model: Qwen2.5-0.5B-Instruct, Q4_0 GGUF (`qwen2.5-0.5b-instruct-q4_0.gguf`),
  loaded via `GpuModel::load` with `fast_kernels = true`.
- LoRA adapter: `idle-intelligence/llm-of-life-lora`'s `lora-a-rules-300.bin`
  (LLMLIFE2 format, rank 8, alpha 16.0, q/k/v/o only, 192 tensors = 24 layers
  x 4 projections x 2 (a, b)): the format actually published today (no
  safetensors/PEFT conversion exists yet).
- Prompt: llm-life variant A's own shape: `variant_a::rules_prefix(Rule::life())`
  + `variant_a::cell_prompt([1,1,1,0,0,0,0,0], 0)` (a birth case), 106 tokens,
  no chat template (llm-life fine-tunes on the raw prompt text directly).
- Reference: `crates/lean/reference/gen_fixture_lora.py`: transformers
  loads the same GGUF (dequantized on load, same mechanism as
  `gen_fixture.py`), the LLMLIFE2 file is parsed directly with `struct`, and
  the LoRA delta (`(x @ a) @ b * alpha/rank`) is added via forward hooks on
  `model.model.layers[i].self_attn.{q,k,v,o}_proj`.
- Engine test: `crates/lean/tests/lora_parity.rs`, run native
  (`cargo test -p lean --release -- --ignored`, `LEAN_GGUF`,
  `LEAN_TOKENIZER_DIR`, `LEAN_LORA_BIN` set to the paths above).

Max abs diff against the PyTorch reference: 0.00016 (dead), 0.00031 (alive) :
inside the fixture's own 2e-2 tolerance (two independent Q4_0 dequant
implementations, not bit-identical, same tolerance class as
`fixture_parity.rs`'s existing 1e-3 top-20 check).

Packed block-diagonal parity (`packed_block_diagonal_matches_per_cell_forward`,
no PyTorch reference needed: checks the packing's own numerical-invisibility
property): two cells (`[1,1,1,0,0,0,0,0],0` and `[0,0,0,0,0,0,0,0],1`) packed
into one chunk against a shared resident prefix, block-diagonal mask,
per-block RoPE restart, versus each cell forwarded alone against the same
snapshotted prefix:

| cell | alone (dead, alive) | packed (dead, alive) |
|---|---|---|
| A | (22.063759, 23.350817) | (22.063759, 23.350817) |
| B | (22.218702, 21.375978) | (22.218702, 21.375978) |

Exact match (both reported to 6 decimal places), confirming the packing is
numerically invisible: the property llm-life's variant A depends on.

## Observations

- The LLMLIFE2 file stores `a` as `[in_features, rank]` and `b` as
  `[rank, out_features]` (the natural `x @ a`, `(..) @ b` orientation).
  `crates/lean`'s existing `linear()` kernel (`linear.wgsl`) expects weights
  in PyTorch/GGUF `[out, in]` row-major layout. The first implementation fed
  `a`/`b` straight through without transposing and under-applied the LoRA
  delta by roughly 5x (dead +0.54 vs the reference's +2.7, alive +0.48 vs
  +4.28): not zero, since the kernel still read *some* value at each
  address, just the wrong one. Fixed by transposing both matrices once at
  upload time (`lora.rs::transpose`), not at every forward call.
- `apply_lora`/`clear_lora` need no base reload: confirmed by running the
  same chunk through the base model, then with LoRA, then with
  `clear_lora()`, and getting the base numbers back exactly.
- `forward_chunk_spec` reuses every existing kernel except three new ones
  (`rope_positions.wgsl`, `attn_chunk_masked.wgsl`,
  `gather_dequant_q8_rows.wgsl`): LoRA itself needed no new kernel at all,
  only two extra `linear()` calls (both plain F32) and one `add_inplace`
  per adapted projection.
