## Observations

- Tool order flips the 12-tool set's correct% (26.7% -> 66.7%) but leaves the 34-tool set's aggregate unchanged (25.0% -> 25.0%, though the per-case pattern differs: s03/m02/m03 flip true->false, m01/m09 flip false->true) — the fix matters far more when there are fewer competing tools.
- Under `--tool-order listing-first`, the model calls `get_households_and_groups_and_players` as its first tool call in 11/15 scored cases at 12 tools (all of s02/s03/s06/s08/s09/m01/m02/m03/m05/m08/m09) but only 8/20 at 34 tools (s02/m01/m02/m03/m05/m08/m09/m10) — the same relative ordering (listing tool first in the preamble) is followed far less reliably once 33 other tools compete for the model's attention.
- `s01`, `s07`, `m04`, `m05`, `m07` are incorrect in all six runs regardless of tool count, order, or system prompt. `s07` ("Skip to the previous track.") never calls a listing tool first in any run — e.g. run a-new calls `skip_to_previous_track({"group_id":"1"})` directly; `m07` ("What's the volume in the bedroom?") likewise invents a room name as the id directly, e.g. run b-new calls `get_group_volume({"group_id":"bedroom"})`.
- `s04`, `s05`, `s10`, `m06` are incorrect in every run where they're scored (34-tool runs b-old/b-new/d) — all four are only solvable under `tools12_ok: false` reasoning paths requiring a correct `household_id`, e.g. run b-new's `s04` calls `get_sonos_playlists({"household_id":"default"})` and `s05` calls `get_registered_music_services({"household_id":"123456789"})`, both invented ids rather than the canonical `Sonos_ABC123XYZ`.
- `s02` and `m08` are correct in all six runs; mean decode throughput is consistently roughly double at 12 tools versus 34 tools regardless of order (5.87/5.59/5.50 tok/s at 12 tools vs. 2.95/2.84/2.87 tok/s at 34 tools) — the longer shared KV-cache prefix slows per-token decode independent of tool order.
- The `ids-from-tools` system prompt (runs c, d) was only tested under alphabetical order; at 12 tools it scores below both listing-first and alphabetical `default` (20.0% vs. 66.7%/26.7%), so which effect dominates — instruction wording or tool order — for the 12-tool set is not disentangled by these six runs.
- Comparing kernels-v2 (e, f) to the morning's listing-first runs at the same tool counts (a-new, b-new): at 13 tools, mean per-case prefill dropped 37.138s -> 25.271s (-32%), mean decode throughput rose 5.59 -> 7.55 tok/s (+35%), mean total time dropped 49.431s -> 34.541s (-30%). At 34 tools, run f shows the opposite direction (prefill 45.442s -> 63.292s, decode 2.84 -> 1.61 tok/s, total 65.588s -> 121.501s) but run f had a confirmed concurrent GPU consumer (`full_forward`/`q4_matmul` test binary) partway through, so this is contention, not a genuine kernels-v2 regression at 34 tools — no clean uncontended 34-tool kernels-v2 timing exists yet.
- m11 ("Play music by Nirvana in the kitchen."): run e calls `get_households_and_groups_and_players({})` then `play_artist({"artist":"Nirvana","group_id":"RINCON_KITCHEN01:1","shuffle":false})` — correct. Run f calls `get_households_and_groups_and_players({})` then `play_artist({"artist":"Nirvana","group_id":"RINCON_KITCHEN01:1"})`, omitting `shuffle` — scored incorrect (missing required call, since `expected.args`'s `shuffle: false` key is absent from the made call).
- m12 ("Ungroup the kitchen."): run e skips it (`remove_players_from_group` isn't in the 13-tool subset). Run f calls `get_households_and_groups_and_players({})` then `remove_players_from_group({"group_id":"RINCON_KITCHEN01:1","player_ids":["RINCON_KITCHEN01","RINCON_KITCHEN02"]})` — scored incorrect: it removed both Kitchen players (including the coordinator, RINCON_KITCHEN01) rather than just the non-coordinator RINCON_KITCHEN02, which would leave the group empty rather than ungrouped.
