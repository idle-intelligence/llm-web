# lean engine perf pass, native + browser

Follow-on to `docs/runs/2026-09-28-lean-web.md`. Same crate (`crates/lean`),
same model/fixture, macOS 26.3.1, Apple M2. Goal: prefill >= 1000 tok/s and
decode >= 80 tok/s in the browser harness, or a profiled explanation of the
remaining gap.

## Parameters

- Model: Qwen2.5-0.5B-Instruct, `qwen2.5-0.5b-instruct-q4_0.gguf` (Q4_0
  weights, Q8_0 `output.weight`), tokenizer `Qwen/Qwen2.5-0.5B-Instruct`.
- Config: 24 layers, hidden 896, 14 heads, 2 KV heads, head_dim 64,
  intermediate 4864, vocab 151936.
- Fixture: `crates/lean/reference/fixture.json` (`short` 36 prompt tokens,
  `long` 86, `non_english` 54, 32-token greedy continuation each), plus a new
  timing-only case `long_1000` added to the harness this session
  (`crates/lean/www/main.js::buildLongPrompt`, 90 repeated distinct
  sentences, actual length reported by the new `LeanEngine.tokenCount()`
  wasm-bindgen method: 1263 tokens after chat-templating).
- Kernel path: `fast_kernels = true` on both native and browser.
- Native: `lean-cli --tokens 32 --kernel fast`, Metal backend via wgpu 26.
- Browser: Playwright-bundled Chromium 153.0.8010.12, headless,
  `--enable-unsafe-webgpu --enable-features=Vulkan,WebGPU --use-angle=metal`,
  served locally (`?local=1`) from `python3 -m http.server` rooted at
  `crates/lean/`. Harness page `crates/lean/www/index.html`, engine build tag
  `2026-09-28-4`. `lean_bg.wasm` sha256
  `aec70e637274ba5c906005e89722ae2cf8f0607a2e8573b8e86cb88dcb211892`
  (verified as the served bytes before every timed run below).
- One GPU job at a time throughout; native and browser runs never overlapped.

## Changes this session

1. **Dispatch-count instrumentation** (`Engine::dispatch_count`, reset/read
   around prefill and the decode loop in `lean_cli.rs` and `web.rs`). Same
   Rust forward-pass code on both targets, so the dispatch count is
   target-independent; only backend per-dispatch overhead differs.
2. **Q4 tiled-matmul kernel size gate** (`model.rs::TILED_MIN_ROWS = 16`):
   `linear()`'s Q4_0 arm previously used the tiled kernel for every prefill
   call (`rows > 1`); it now only uses the tiled kernel at `rows >= 16` and
   falls back to the naive per-element kernel (`linear_q4.wgsl`) for
   `2 <= rows < 16`, per the brief's instruction that the tiled kernel only
   needs to win at `M >= 16`. Does not change behavior for this session's
   fixture/timing cases (prefill `M` is always >= 36), so it has no measured
   effect on the numbers below - it only prevents a regression on
   hypothetical small-M prefill calls (e.g. a short speculative-decode
   window) that this session's cases don't exercise.
3. **GPU argmax for decode** (`shaders/argmax.wgsl`, new; single workgroup,
   256 threads, tree reduction over the vocab). `forward_decode_step_argmax`
   (`model.rs`) records the argmax dispatch in the same encoder/submit as
   the rest of the decode step and reads back one `u32` (4 bytes) instead of
   the full `vocab_size * 4`-byte logits vector (~608KB for this model's
   151936-token vocab). `forward_decode_step` (full-logits readback) is kept
   for future samplers; `lean-cli` and `web.rs`'s `generate()` both switched
   to the argmax path for greedy decoding.

## Observations

- Dispatch count is identical across the three fixture cases regardless of
  prompt length (363 for prefill, 364 for one decode step) because prefill
  and decode each run the same fixed op graph (24 layers x ~15 dispatches +
  embed/norm/lm_head) once per call, independent of `M` - only the tiled/naive
  kernel choice inside each `linear()` call changes with `M`, not the
  dispatch count. Decode's count (364) is exactly prefill's (363) plus the
  one argmax dispatch added this session.
- Per-dispatch overhead, computed from decode's fixed 364-dispatch count:
  native ~51.5-52.3ms/364 = ~141-144us/dispatch; browser ~26.5-26.9ms/364 =
  ~73-74us/dispatch. The browser is faster per-dispatch than native wgpu-Metal
  on this machine, consistent with `2026-09-28-lean-web.md`'s
  "browser faster than native" observation - now with a shared, target-
  independent instrumentation (dispatch count) behind it rather than two
  differently-scoped wall-clock numbers. This does not explain *why* wgpu's
  native Metal path is slower per dispatch than the browser's WebGPU-over-
  ANGLE-Metal path; that would need per-backend GPU-side profiling
  (Instruments/Metal System Trace for native, `chrome://tracing` for
  browser) not run this session.
- GPU argmax (item 3 above) did not move decode ms/token outside noise on
  either target (browser short-case delta ~0, see the before/after table).
  This means the ~608KB full-logits readback was not the decode bottleneck
  at this model's vocab size on this machine (Apple Silicon's unified memory
  makes the readback itself cheap; on a discrete-GPU device with a real
  PCIe copy this would likely matter more). The change is kept because it
  is strictly less work (4 bytes vs. 608KB) and removes a full CPU-side
  vocab-size argmax scan per step, but it should not be reported as a
  decode-speed fix - only as a change, per this crate's own rule against
  calling something a fix before it's measured to move the number.
- Prefill tok/s scales up with prompt length within this session's data (93.7
  at 36 tokens, 189.1 at 86, 236.2 at 1263) but plateaus far short of the
  >= 1000 target even at 1263 tokens, where per-dispatch/launch overhead
  should be least significant relative to the GEMM's actual FLOPs. A rough
  compute-bound estimate for the `long_1000` case (24 layers x [896x896 q +
  2x896x128 kv + 896x896 o + 2x896x4864 gate/up] matmuls, MACs x2 for FLOPs,
  ignoring attention/norm/lm-head as a rounding error next to the matmuls)
  gives ~904 GFLOP total across the 1263-token prefill (896x896 q/o, 2x
  896x128 k/v, and 3x 896x4864 gate/up/down per layer, MACs x2, x24 layers,
  x1263 tokens); at 5.35s wall time that is ~169 GFLOP/s achieved, well under
  the M2 GPU's quoted ~3.6 TFLOP/s FP32 peak (~4.7% of peak). This points at
  the tiled Q4_0 kernel's own efficiency (scalar
  per-element dequant inside the tile loop, 16x16/MICRO=4 register tiling,
  no vectorized loads) as the dominant remaining cost for prefill, not
  dispatch fragmentation - consistent with `linear_q4_tiled.wgsl`'s own doc
  comment calling out that it was already a known-imperfect port. This
  session did not rewrite that kernel (a vectorized/larger-tile Q4_0 GEMM
  kernel is a distinct, multi-hour WGSL kernel-design task, not a
  same-session follow-on to instrumentation and gating work) - flagged here
  as the concrete next step rather than attempted under this session's time
  budget.
- Native per-kernel GPU timestamp profiling (`wgpu::Features::TIMESTAMP_QUERY`)
  was not implemented this session. Chromium's WebGPU implementation does
  not expose timestamp queries to content by default (the feature requires
  an origin trial / experimental flag not enabled by this harness's
  `--enable-unsafe-webgpu` flag set), so a same-instrumentation per-op
  breakdown across both targets was not achievable without diverging the
  native and browser measurement methods - the dispatch-count metric above
  was used instead as the one metric genuinely shared by both.
- `cargo test -p lean --release -- --ignored fixture_parity` (env
  `LEAN_GGUF`/`LEAN_TOKENIZER_DIR` set) passes token-exact after all three
  changes (`test fixture_parity_both_kernel_paths ... ok`, 24.84s). Browser
  harness `window.__leanResult.allMatch === true` for all three fixture
  cases after the wasm rebuild (`lean_bg.wasm` sha256 above, `ENGINE_BUILD =
  "2026-09-28-4"`, verified served before the timed run). `cargo clippy -p
  lean --all-targets --release -- -D warnings` and `cargo clippy -p lean
  --lib --target wasm32-unknown-unknown --no-default-features --features web
  -- -D warnings` both clean.

## Update 2026-09-28: vec4-packed Q4_0 tiled GEMM

Follow-on session, same machine/model/harness. Rewrote
`linear_q4_tiled.wgsl` per this doc's own "scalar per-element dequant, no
vectorized loads" finding above: `x`/`qs` bound as
`array<vec4<f32>>`/`array<vec4<u32>>` (both always 16-byte-aligned - `K`
and Q4_0's 32-element block are always multiples of 4), `w_tile`/`x_tile`
as `vec4<f32>` arrays at the same total shared-memory footprint as before
(2048 f32 == 512 vec4), inner product loop using `dot()` over 8 vec4
groups instead of 32 scalar multiply-adds, dequant done by one thread per
output row (one `vec4<u32>` load = the whole 16-byte block) instead of 4
threads each loading one word. Same session also fixed a length-independent
attention correctness bug (see `docs/runs/2026-09-28-lean-long-context.md`)
that changes the numbers below at real long-context lengths - noted per
row.

Engine build `2026-09-28-6`, `lean_bg.wasm` sha256
`c5ea389097c18b0486822181c2d16f6b4f268f9bb44a33cd4a7d226c5cd3da20`
(verified served before every timed run below).

### Observations

- The vec4 GEMM rewrite gives a genuine 12-20% prefill speedup at
  short/medium prompt lengths (36-86 tokens), where the FFN GEMM (not
  attention) dominates prefill cost - consistent with this doc's original
  ~4.7%-of-peak finding pointing at the GEMM kernel specifically. Decode is
  flat as expected: `linear_q4_decode.wgsl` (the coalesced matvec kernel
  used for decode's M=1 case) is unchanged; this rewrite only touched the
  M>=16 tiled prefill path.
- The long-context rows are not a before/after comparison for this GEMM
  change: the same session also fixed `attn_prefill.wgsl`/
  `attn_decode.wgsl`'s fixed-size caps (256/2048 tokens), which were
  silently producing incomplete (wrong) attention output past those
  lengths - including this doc's original `long_1000` row above. The
  124-126 tok/s prefill numbers at 1500-2354 tokens are the cost of
  *correct* O(seq^2) causal attention with today's per-thread kernel (no
  shared-memory K/V reuse across query threads), not a regression from the
  236.2 tok/s `long_1000` number above, which was computed over an
  incorrectly-truncated attention window. Still far under the >=1000 tok/s
  target - closing that gap needs a genuinely tiled flash-attention
  kernel, which neither session attempted.
- Full per-case detail (including native timings and the KV-snapshot
  >256-token restore) is in `docs/runs/2026-09-28-lean-long-context.md`.
